## 왜 계획을 먼저 시키나요?

AI 코딩 도구는 요청을 받는 즉시 코드를 쓰기 시작합니다. 작은 조각에서는 그게 빠르지만, 파일 서너 개가 얽힌 작업(로그인 붙이기, 데이터 구조 바꾸기)에서는 **중간에 방향이 틀렸다는 걸 뒤늦게** 알게 됩니다.

해결은 간단합니다. **"아직 코드 쓰지 마"** 를 먼저 말하는 것.

## 계획 요청의 형태

> "로그인 기능을 추가하려고 해. 아직 코드는 쓰지 말고:
> 1. 어떤 파일을 새로 만들고 어떤 파일을 고칠지
> 2. 어떤 순서로 할지
> 3. 내가 미리 준비해야 할 것(계정, 키, 설정)
> 을 알려줘. 내가 확인하면 시작하자."

많은 도구에 이런 **계획 모드**가 내장되어 있습니다(코드를 못 쓰게 잠그고 읽기와 제안만 하는 모드). 있으면 쓰고, 없으면 위처럼 말로 합니다.

계획을 받으면 **읽고 고칩니다.** "3번은 필요 없어", "2번 먼저 해", "새 라이브러리는 안 돼". 여기서 5분 쓰면 뒤에서 1시간이 절약됩니다.

## 맥락(context)이란

AI는 대화 안에서 읽은 파일과 주고받은 말을 기억합니다. 이걸 맥락이라고 하는데, **한도가 있고, 많아질수록 품질이 떨어집니다.** 대화가 길어지면 AI가 앞에서 한 약속을 잊거나 이미 고친 파일을 다시 고칩니다.

### 맥락을 깨끗하게 유지하는 규칙

1. **조각이 끝나면 새 대화.** 가장 중요합니다.
2. **필요한 파일만 지목**: "프로젝트 전체를 보고"보다 "@src/components/MenuCard.tsx 를 보고".
3. **긴 로그는 요약해서**: 에러 500줄을 붙여넣지 말고 마지막 30줄만.
4. **규칙은 대화가 아니라 파일에**: 매번 말하는 규칙은 CLAUDE.md로 (다음 스킬).

### 대화가 길어졌을 때

대부분의 도구에 **압축(compact)** 기능이 있습니다. 지금까지 대화를 요약해 맥락을 줄이는 것인데, 세부가 날아갈 수 있으니 그 전에 이렇게 하는 게 안전합니다.

> "지금까지 한 것과 남은 것을 TODO.md에 정리해줘."

그리고 새 대화를 시작해 "TODO.md 읽고 이어서 하자"로 시작합니다. 파일이 기억을 대신합니다.

## 작업 크기별 접근

| 작업 | 방식 |
|---|---|
| 한 파일, 한 기능 | 바로 요청 (7강 템플릿) |
| 여러 파일, 한 기능 | 계획 먼저 → 승인 → 실행 |
| 구조 변경 (폴더 정리, DB 스키마 변경) | 계획 → 커밋 → 실행 → 즉시 확인 → 커밋. 새 브랜치에서 |
| 뭘 해야 할지 모름 | "선택지 3개" 요청 (프롬프트 모음 참고) |
